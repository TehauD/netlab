# Security Policy

## Scope

netlab processes a file containing the names, employers, and profile URLs of everyone in
your professional network. Anything that could expose that data is in scope, including:

- A code path that transmits connection data off the machine
- Persistence of uploaded data to disk
- Connection contents appearing in logs
- Cross-site scripting via unescaped CSV-derived text in the UI
- Path traversal or arbitrary file read through the static mount

## Reporting

Open a **private security advisory** through the repository's Security tab rather than a
public issue. Include reproduction steps and the affected version. Please use synthetic data
generated by `netlab sample` — never attach a real export.

Expect an acknowledgement within 72 hours.

## Design guarantees

These are enforced by tests and by CI, and are treated as invariants:

| Guarantee | How it is enforced |
| --- | --- |
| No outbound network calls | No HTTP client is imported anywhere in the package |
| No persistence | Uploads live in the request scope; no database, cache, or temp file |
| Loopback by default | `NETLAB_HOST=127.0.0.1`, with a startup warning when overridden |
| Logs carry no contents | Counts, durations, and error classes only |
| Output escaping | All CSV-derived text passes through `esc()` before reaching `innerHTML` |
| No third-party JavaScript | The UI is three static files plus six local ES modules |
| No exports in the repo | A CI job fails the build if a connections CSV is ever tracked |

## Verifying the no-egress claim

Run the server and watch for outbound sockets while analyzing a file:

```bash
netlab serve &
lsof -i -P -n | grep -i python     # macOS / Linux
```

You should see the listening socket on 127.0.0.1:8787 and nothing else.
